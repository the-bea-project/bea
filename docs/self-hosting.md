# How Bea builds Bea

Bea transpiles to Gleam, and Bea's compiler is written in Bea. The
repository is an ordinary Bea project:

| Path | What it is |
| --- | --- |
| `bea.toml`, `manifest.toml` | The project (the package is `bea`, its main module `bea`). |
| `src/` | The compiler, formatter, language server and CLI: Bea modules, plus the Erlang FFI `bea_ffi.erl` and `bea_signal.erl`. |
| `test/` | The test suite, in Gleam (gleeunit), run by `bea test`. |
| `scripts/bea` | Runs the compiler this checkout has built (`.beabuild/build/dev`). |

Gleam stays the backend: `bea build` compiles `src/` to Gleam in
`.beabuild/` and Gleam builds that, exactly as for any Bea project.

## Building

A Bea project is built by a `bea`, so building Bea needs one: the
standalone binary from the releases page, or any `bea` you built before.

```sh
bea build            # your bea compiles src/ into .beabuild/, Gleam builds it
scripts/bea build    # the compiler just built rebuilds itself
scripts/bea test     # and runs the tests
bea pack             # the binary, build/bea (with gleepack)
```

The second build matters when a change affects the Gleam the compiler
generates: the first build of that change is compiled by the old compiler,
the second by the new one. For the compiler's own source the two normally
generate the same Gleam (a fixed point), which you can check by comparing
`.beabuild/src` after each.

The compiler's source must be compilable by the `bea` that builds it. If
`src/` starts using a feature added in the same change, build with a `bea`
that has it: build the change in two steps (first the feature, then its
use), or build with `scripts/bea` from a checkout that has the feature.

`test/self_hosting_test.gleam` checks, from the test suite, that the
compiler under test compiles its own source with no error or warning.

## Releases

A release's binary is the compiler packed by itself:

```sh
bea build && scripts/bea build && scripts/bea test
scripts/bea pack -o build/bea-linux-amd64
```

CI (`.github/workflows/test.yml`) downloads `bea-linux-amd64` from the
latest release to build the checkout, so each release should carry it
(and binaries for other platforms as wanted: `bea pack -t <target>`).

## Without any bea

The last revision of the compiler written entirely in Gleam, "Record
shorthand, parser fix and keyword renames (bootstrap seed)" (`4364053`, git
tree `4cd8c7015369b3dc5334c18565133c8277a0e622`), builds with Gleam alone,
and its compiler can build the current one as long as `src/` uses no syntax
newer than it:

```sh
git worktree add ../bea-gleam 4364053
(cd ../bea-gleam && gleam build)
../bea-gleam/scripts/bea build     # in this checkout
scripts/bea build                  # then as usual
```

## How the compiler was migrated

The compiler was written in Gleam until the migration recorded in the
history: every module was translated to Bea mechanically (Bea reads most of
Gleam's syntax, so only what Bea spells differently was rewritten),
formatted with `bea format`, and checked to be the same program as the
Gleam original by parsing both and comparing them definition by
definition. A trusted bootstrap built the all-Gleam seed above, used it to
compile the Bea sources (compiler B), used B to compile them again
(compiler C), and required the Gleam generated by the seed and by B to be
identical byte for byte, and the test suites to pass with B and C. That
tooling was removed once the compiler built itself; it is in the history
with the commit "Self-host the Bea compiler".
